I'll be honest. When someone says "object storage for AI" the picture in most people's heads is a purpose-built S3 appliance with a six-figure invoice attached, or a hyperscaler bucket with an egress meter running. Swift, the OpenStack object store that has been quietly holding petabytes since 2010, rarely makes the list. It's old. It doesn't have a launch video. It speaks S3 through a middleware rather than natively.

Our team has been leaning on that middleware harder every month. Model weights, training shards, and lately the KV cache that vLLM spills out of GPU memory all land in Swift buckets through the S3 API, and at some point "it seems fine" stops being an acceptable answer to "how fast is it." So we did what you're supposed to do. We picked an open source benchmark, built a container around it, ran the object sizes that AI workloads actually produce, and kept the numbers.

<!-- more -->

This is what we measured in the DFW3 region of Rackspace OpenStack Flex, what the numbers mean in plain terms, and where I think Swift fits for modern S3-compatible workloads. Everything below was produced with tools you can download today, and the two gotchas that cost us an afternoon are in here so they don't cost you one.

## The oldest service in the room

Swift shipped in the very first OpenStack release. It was one of two projects, alongside Nova, and it has been in continuous production somewhere on earth ever since. Its native API is its own thing, with accounts, containers, and objects, but since 2018 it has carried an `s3api` middleware in-tree that translates the S3 dialect on the fly: SigV4 signatures, multipart uploads, range reads, bucket listings, the lot. Multipart uploads become Swift's static large objects under the hood, and a Keystone EC2 credential stands in for an AWS access key pair.

What that gives a tenant is a durable, replicated, region-scale object store that any S3 client already knows how to talk to. What it does not give you, out of the box, is a number. The Swift documentation will tell you what's supported. It will not tell you how many 32 MiB objects per second you'll get from a single VM in DFW3. That's on us.

## What an AI workload actually asks of object storage

"AI workload" is not one access pattern. It's at least four, and they stress different parts of the stack.

**KV-cache offload.** Inference engines like vLLM, with LMCache attached, push key-value cache blocks out of GPU memory to CPU, then to disk, then to an object store, and pull them back on a prefix hit. The objects are the size of a KV chunk, which on our 27B-class models with fp8 cache is about 34 MiB, and the pattern is write-heavy with a constant trickle of existence checks. Latency at the tail is what stalls a prefill.

**Model weights.** Safetensors shards are 2 to 5 GiB each and loaders read them either whole or as a stream of range requests. This is pure bandwidth, and time to first byte matters because a loader issues thousands of them.

**Training data.** Two shapes. Tokenized or WebDataset shards are a few hundred MiB read sequentially by many workers. Raw samples, images and audio, are hundreds of KiB to a few MiB each, wildly variable, and read at a rate that is bounded by requests per second more than by bytes.

**Metadata.** Manifests, tokenizer files, dataset indexes, and the bucket listings that enumerate all of the above. Kilobytes each. This is where transaction cost and listing latency live.

So instead of one number we built a matrix: 20 variants across those four shapes, from 4 KiB objects to 1 GiB objects, from 4 concurrent streams to 64.

## The tooling: warp in a container and two small scripts

[warp](https://github.com/minio/warp) is MinIO's S3 benchmark client. It's open source, it's one static binary, and it produces a compressed JSON record of every run that you can analyze later. We wrapped it in a container so that credentials never live anywhere but the environment of a running process. The whole Dockerfile fits on a napkin.

The entrypoint adds the one flag Swift needs, `--lookup path`, and hands everything else to warp. Around that we have a 200-line bash driver that walks the matrix, reuses a preloaded bucket for the read-only variants so we don't upload eight 1 GiB objects four times, and a Python aggregator that turns every run's JSON into one table with transactions per second, throughput, and latency percentiles. Nothing exotic. Docker, bash, Python, and a benchmark tool.

> You can downlaod and reproduce anything that is written here using my handy-dandy [repo](https://github.com/cloudnull/warp-swift-bench)

Two things bit us on the first request, and they'll bite you too.

**The region is not decorative.** SigV4 puts a region string in the credential scope, and s3api compares it to the `location` it was configured with. In DFW3 that value is `DFW3`, not `us-east-1`, and if you get it wrong warp just says `400 Bad Request` because its first call is a HEAD with no body. Ask the endpoint with a signed curl and it tells you exactly what it wants:

```shell
curl -sS --aws-sigv4 "aws:amz:us-east-1:s3" --user "$ACCESS:$SECRET" \
  -H "x-amz-content-sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" \
  https://swift.api.DFW3.rackspacecloud.com/
# <Code>AuthorizationHeaderMalformed</Code><Message>... expecting 'DFW3'</Message>
```

**Path style only.** Swift's s3api expects `/<bucket>/<key>`. There is no wildcard DNS and no wildcard certificate for `<bucket>.swift.api.DFW3.rackspacecloud.com`, so any client that insists on virtual-hosted addressing will fail in ways that look like everything except an addressing problem. Most clients have a switch. Flip it.

With those two set, a run looks like this. Credentials come from `openstack ec2 credentials create` and are passed by name so they never touch the command line:

```shell
docker run --rm -it \
  -e WARP_HOST=swift.api.DFW3.rackspacecloud.com -e WARP_REGION=DFW3 \
  -e WARP_ACCESS_KEY -e WARP_SECRET_KEY \
  -v "$PWD/results:/data" \
  warp-swift-bench mixed --duration 2m --obj.size 32MiB --objects 200 --concurrent 16
```

## What we measured

### A word on methodology

These are, in the technical parlance of our industry, trust-me-bro benchmarks. One client VM. One region. One afternoon. Run by the people who operate the thing, against the thing, with a tool they picked. Nobody from a standards body was in the room, and the only peer review was a Teams thread. I want that stated plainly, because every vendor benchmark you have ever read had the same provenance and a nicer font.

What separates trust-me-bro from marketing is whether you can run it yourself. You can. The [container](https://github.com/cloudnull/warp-swift-bench) is thirty lines, the driver is one file, and neither of them knows who you are. Until you do, here is what we saw. All numbers are from a single client VM in DFW3, two minutes per variant, against the shared Swift service; the call out here is that we're running benchmarks against production systems in a public cloud. TPS is successful S3 operations per second inside warp's trimmed measurement window. A multipart upload counts as one PUT, even if we ran 10K PUTs to put the pieces together.

### The KV-cache tier

This is the mixed workload: 40 percent PUT, 40 percent GET, 10 percent STAT, 10 percent DELETE, at the three object sizes that bracket a real KV chunk.

| Object | Streams | Aggregate | TPS | PUT p50 | GET p50 | GET first byte | STAT p50 |
|--------|--------:|----------:|----:|--------:|--------:|---------------:|---------:|
| 8 MiB  | 8  | 421 MiB/s   | 66  | 174 ms | 95 ms    | 17 ms | 9 ms  |
| 8 MiB  | 16 | 852 MiB/s   | 133 | 173 ms | 107 ms   | 17 ms | 9 ms  |
| 32 MiB | 8  | 679 MiB/s   | 26  | 354 ms | 333 ms   | 24 ms | 10 ms |
| 32 MiB | 16 | 1,034 MiB/s | 40  | 362 ms | 583 ms   | 25 ms | 11 ms |
| 64 MiB | 8  | 817 MiB/s   | 16  | 394 ms | 785 ms   | 25 ms | 10 ms |
| 64 MiB | 16 | 1,062 MiB/s | 21  | 445 ms | 1,485 ms | 26 ms | 10 ms |

Read that table twice, because there are two stories in it.

The first is that going from 8 to 16 streams at 8 MiB doubles everything, and PUT latency doesn't move. Swift wasn't breathing hard. The second is that at 32 and 64 MiB the aggregate flattens at just over 1 GiB/s no matter what we do, and GET latency climbs in lockstep with the number of bytes in flight: 16 streams times 64 MiB is a gigabyte queued behind a link that moves a gigabyte a second, and the median GET obligingly takes a second and a half. That ceiling shows up in every large-object test in this post. It is close to 9 gigabits, which is a 10 gigabit path on the client side running flat out against a ratelimited and QOS'd VM's on the OpenStack Flex public cloud network.

What this means for an inference node: a 34 MiB KV chunk stores in roughly 360 ms at the median and under half a second at the 99th percentile with 16 in flight, the existence check that precedes a cache hit costs 10 ms, and the first byte of the chunk comes back in 25 ms. A node rehydrating 2 GiB of cache gets it in about four seconds. On inference nodes, that's fast enough that the object tier is a real third tier and not a backup.

### Multipart or not

s3api turns multipart uploads into static large objects, and we wanted to know what that costs. warp switches to multipart above 16 MiB, so we ran the 32 and 64 MiB variants both ways.

| 64 MiB, 8 streams | PUT p50 | PUT p99 | GET p50 | Aggregate |
|-------------------|--------:|--------:|--------:|----------:|
| Multipart, 16 MiB parts | 394 ms | 631 ms | 785 ms | 817 MiB/s |
| Single PUT              | 731 ms | 894 ms | 689 ms | 729 MiB/s |

At 32 MiB the two are indistinguishable. At 64 MiB, multipart nearly halves write latency because the parts upload in parallel, while reading a manifest-backed object costs 14 to 20 percent more GET latency. For a write-heavy cache tier that trade is worth taking. For a read-mostly dataset it's not, and the client decides, which is the right place for that decision to live.

### Model weights

Whole-object reads of 1 GiB objects, and the same objects read as 64 MiB ranges the way a safetensors loader does.

| Pattern | Streams | Aggregate | Per request p50 | First byte |
|---------|--------:|----------:|----------------:|-----------:|
| Whole 1 GiB    | 4 | 457 MiB/s | 9.0 s  | 25 ms |
| Whole 1 GiB    | 8 | 638 MiB/s | 12.1 s | 41 ms |
| 64 MiB ranges  | 4 | 447 MiB/s | 616 ms | 25 ms |
| 64 MiB ranges  | 8 | 630 MiB/s | 817 ms | 25 ms |

Range reads cost nothing. Same aggregate as whole objects, same time to first byte, and a loader that wants tensor 47 of 300 gets it without pulling the shard. Per stream we saw 80 to 115 MiB/s, so a loader that opens 16 or more streams, which every modern one does, will hit the same 1 GiB/s wall as the cache tier. In practical terms: a 5 GiB shard lands in about eight seconds at 8 streams, and a 70 GB checkpoint on one node is under two minutes. That's a cold start you can live with.

### Training data

| Shape | Streams | Aggregate | TPS | Note |
|-------|--------:|----------:|----:|------|
| 256 MiB shards       | 32 | 1,044 MiB/s | 3.9   | p50 7.9 s per shard, 32 in flight |
| Samples up to 4 MiB  | 32 | 925 MiB/s   | 1,272 | random sizes |
| Samples up to 4 MiB  | 64 | 1,086 MiB/s | 1,494 | random sizes |

The shard case is the link again: a terabyte of shards pulled onto one node takes about 17 minutes, and the only way to go faster is to have bigger nodes with more generous QOS and/or more nodes, which is how training jobs are shaped anyway. The sample case is the more interesting one, because it isn't bandwidth-bound until 64 streams. One VM served roughly 1,500 variable-size objects per second with no errors, which is more than most data loaders can consume before the GPUs become the bottleneck.

### Small transactions and listings

The floor for any S3 transaction here is the STAT call: 9 to 10 ms at the median and 11 to 16 ms at the 99th in all but one KV variant. DELETE runs 27 to 43 ms. Listing we only ran as a ten-second shakedown against small prefixes, so treat it as a first look: a list call returned in 75 ms at the median and 163 ms at the 99th, 200 calls per second from 16 streams. The full listing story, with deep prefixes and million-object containers, deserves its own run and will get one.

## The TPS breakdown, and the one number you came here for

Everyone asks for TPS. Nobody asks what a transaction is, so let me define it before I count it: one successful S3 operation, start to finish, GET or PUT or HEAD or DELETE, inside warp's measurement window. A multipart upload is one transaction no matter how many parts it took, which honestly doesn't do me any favors on the trust me bro scale of greatness, but we're keeping the numbers honest from start to finish.

| Workload | Object | Streams | TPS | Read | Write |
|----------|--------|--------:|----:|-----:|------:|
| KV cache, mixed | 8 MiB  | 8  | 66    | 33    | 33  |
| KV cache, mixed | 8 MiB  | 16 | 133   | 66    | 67  |
| KV cache, mixed | 32 MiB | 8  | 26    | 13    | 13  |
| KV cache, mixed | 32 MiB | 16 | 40    | 20    | 20  |
| KV cache, mixed | 64 MiB | 8  | 16    | 8     | 8   |
| KV cache, mixed | 64 MiB | 16 | 21    | 10    | 10  |
| Weights, whole  | 1 GiB  | 8  | 0.6   | 0.6   |     |
| Weights, ranged | 64 MiB | 8  | 9.8   | 9.8   |     |
| Dataset shards  | 256 MiB | 32 | 3.9  | 3.9   |     |
| Samples         | up to 4 MiB | 32 | 1,272 | 1,272 | |
| Samples         | up to 4 MiB | 64 | 1,494 | 1,494 | |

> The single-PUT variants of the 32 and 64 MiB rows landed within a transaction per second of their multipart twins, so they're not repeated here.

Three things fall out of that table.

**Above 32 MiB, TPS is just the pipe divided by the object.** Take any large-object row, multiply the GET and PUT transactions by the object size, and you get the same 1 GiB/s wearing a different hat. Forty transactions of 32 MiB, twenty of 64 MiB, four of 256 MiB. Swift isn't deciding those numbers; the client's link is. Pick an object size and I'll tell you the TPS without running anything, which is either a very useful property or a very boring one depending on what you were hoping to learn.

**Below 8 MiB, TPS is what you get, and it's a lot.** The 8 MiB cache tier doubled cleanly from 66 to 133 when we doubled the streams, with no movement in latency, so we did not find its ceiling. The sample workload found one at 1,494, with 64 streams and the link nearly full, and zero errors over the two minutes.

**The transaction floor is 9 milliseconds.** That's a HEAD, median, at every object size we tried. Little's law says one stream can do about 106 of those per second, and 64 streams could do something near 6,800 on a metadata-only workload. We did not run that one. It's arithmetic, not a measurement, which makes it the most trust-me-bro number in this post, and I'm only including it so you can tell me I'm wrong.

Now the aggregate. Seventeen variants, thirty-four minutes of measurement, somewhere north of 380,000 transactions. The mean variant did 188 transactions per second. The median variant did 21. The best did 1,494. You can see the problem with averaging a 1 GiB whole-object read against a 4 MiB sample fetch, which is why nobody publishes the mean and everybody publishes the peak.

So here it is, the number we landed on, the one that goes on the slide: **1,500 transactions per second, per client.**

Small objects, 64 streams, two minutes, no errors, rounded up by six; that is the least any vendor has ever rounded. If your objects are 32 MiB the number is 40 and the pipe is full, and if they're 1 GiB the number is less than one and the pipe is still full. TPS without an object size is a number without a unit. Now you have both, and you know exactly how much to trust each of them. Bro.

## Things to know before your first request

**The region string and path style.** Both covered above, both take thirty seconds once you know, both take an afternoon if you don't. Set `DFW3`, set path style, move on with your life.

**One client fills a 10 gigabit link.** Every large-object number in this post stopped at the same place, and that place is the VM's network, not Swift. The useful consequence is that the question for a big job stops being "how fast is Swift" and becomes "how many VMs do I want," which is a question with a very simple answer on a cloud. We haven't measured where the region itself tops out. That's the next post, and it will need more than one VM and more than one afternoon.

**Multipart is a client decision, and a good one for writes.** It halved write latency at 64 MiB and costs a little on reads of the resulting manifests. Turn it on for cache tiers and checkpoints, leave it off for read-mostly datasets.

## So, can you run modern S3 workloads on it?

Yes, and I'll be more specific than that, because "yes" is what everyone says.

For KV-cache offload it's a good fit today. Sub-second stores at the tail, 10 ms existence checks, 25 ms to first byte, and the client never has to know it isn't talking to AWS. Set the region, set path style, enable multipart, and point LMCache's S3 adapter at it.

For model loading it's a good fit with a caveat. Per-stream throughput is fine and range reads are free, so any loader that parallelizes will fill the pipe. The pipe is the VM's, so if you need a 70 GB model on 20 nodes in under a minute, that's 20 pipes, and it works.

For training data it's a strong fit for the sample-heavy case, where 1,500 objects per second per node is more than a GPU can eat, and an honest fit for the shard case, where you're bandwidth-bound like you'd be anywhere and should spread readers across nodes.

For metadata-heavy pipelines it's adequate. Ten milliseconds per transaction and 75 ms per listing page are not exotic numbers in either direction. If your pipeline does a million HEADs before it does any work, redesign the pipeline.

The part I keep coming back to is that none of this required anything proprietary. A 16-year-old open source object store, an in-tree S3 translation layer, a benchmark tool written by another object store's maintainers, and a bash script. The whole matrix runs in about an hour and produces a table you can put in front of a finance team. That's the thing OpenStack has always been good at: not the fastest number on the slide, but always a good number and a number you can reproduce, on hardware you can see, with software you can read.

## Getting started

If you're on Rackspace OpenStack Flex today, everything in this post works against the Swift endpoint in your region with an EC2 credential from Keystone. If you're running Swift anywhere else, the only thing that changes is the hostname and the region string, and the curl one-liner above will tell you the region.

1. The [Swift s3api documentation](https://docs.openstack.org/swift/latest/middleware.html#module-swift.common.middleware.s3api.s3api) covers what the middleware supports and how `location` is configured.
2. The [Keystone EC2 credentials guide](https://docs.openstack.org/python-openstackclient/latest/cli/command-objects/ec2-credentials.html) is where the access key pair comes from.
3. [warp](https://github.com/minio/warp) is the benchmark, and `warp analyze --json` is the undocumented flag that made our aggregation possible.
4. The [Rackspace OpenStack Flex documentation](https://docs.rackspacecloud.com/) has the endpoints for every region.
5. Code to reproduce these benchmarks is available in the [GitHub repository](https://github.com/cloudnull/warp-swift-bench).

If you run these against your own bucket and get a different shape of results, I'd like to hear about it. If you get better ones, I'd like a screenshot, because at that point it's your trust-me-bro benchmark and I'm the one doing the trusting.
